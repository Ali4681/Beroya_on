# تذكرة Flutter — إلغاء بعد الوصول + تصحيح الالتقاء + السجل الزمني / الخلاف المالي

موجّهة لمطوّر تطبيقات السائق والعميل.
الـBackend جاهز في `Beroya_on` (مع migration `20261018120000_pickup_source_amend`). **لم يُنفَّذ أي شيء في Flutter بعد.**

المراجع: `CANCELLATION_POLICY.md` · هذه التذكرة تغطي بنود السائق **13 و 14 و 16** ومسار الإدارة للخلاف المالي.

---

## القواعد المشتركة

1. **لا رسوم إلغاء نقدية على العميل** في السياسة الحالية — لا تعرض «غرامة» أو مبلغ يُخصم من العميل عند الإلغاء بعد وصول السائق.
2. **تعويض السائق النقدي** (إن اعتمدته الشركة) يتم من لوحة المكتب فقط — ليس زراً في التطبيق يخترع مبلغاً.
3. **GPS وحده ليس دليلاً قاطعاً** في النزاعات؛ اعتمد طوابع الخادم + إقرار السائق بالوصول.
4. لا تخزّن توكنات أو بيانات مالية في `SharedPreferences`.

---

## 13. الراكب يلغي بعد وصول السائق

### السياسة الفعلية

| مرحلة الرحلة | إلغاء العميل | أثر نقدي على العميل | نقاط (مخفية) |
| --- | --- | --- | --- |
| SEARCHING | مسموح | لا | لا |
| DRIVER_ASSIGNED (داخل النافذة المجانية) | مسموح | لا | لا |
| DRIVER_ASSIGNED (بعد النافذة) | مسموح | لا | إلغاء متأخر |
| DRIVER_EN_ROUTE / **ARRIVED** | مسموح | **لا** | إلغاء أثناء التوجه/الوصول (أعلى) |
| IN_PROGRESS | ممنوع من التطبيق | — | — |

السائق **لا يستطيع** الإلغاء بعد `ARRIVED` (فقط قبل الوصول). بعد الوصول: انتظار عدم حضور (`FLUTTER_NO_SHOW.md`) أو انتظار إلغاء العميل.

### APIs

| الغرض | المسار |
| --- | --- |
| معاينة قبل الإلغاء (عميل) | `GET /customer/rides/:rideId/cancel-preview` → `can_cancel`, `late_cancel`, `en_route_cancel`, `free_cancel_until` |
| إلغاء | `POST /customer/rides/:rideId/cancel` + `Idempotency-Key` |
| الاستجابة / الحدث | `cash_fee: false` دائماً في السياسة الحالية |

### Socket للسائق

`ride.customer_cancelled`:

```json
{
  "ride_id": "…",
  "status": "CANCELLED_BY_CUSTOMER",
  "cancelled_at": "…",
  "late_cancel": false,
  "en_route_cancel": true,
  "assigned_at": "…",
  "arrived_at": "…",
  "created_at": "…",
  "cash_fee": false
}
```

### واجهة السائق عند الإلغاء

1. أغلق شاشة الرحلة فوراً.
2. رسالة واضحة حسب الحالة:
   - `en_route_cancel: true` (يشمل بعد الوصول): «ألغى الراكب الرحلة بعد توجهك / وصولك. لا يُخصم مبلغ من الراكب من التطبيق.»
   - غير ذلك: «ألغى الراكب الرحلة.»
3. **لا** تعرض مبلغ تعويض متوقعاً.
4. اعتراض / خلاف: زر «تواصل مع الدعم» يفتح قناة الدعم الموجودة لديكم مع رقم الرحلة `public_number` — الإدارة تراجع من السجل الزمني والمحفظة (القسم 16). لا تختلق مسار شكوى سائق مالي في التطبيق بدون API.

### واجهة العميل عند الإلغاء بعد الوصول

1. استدعِ `cancel-preview` قبل التأكيد.
2. إن `en_route_cancel`: وضّح أن الإلغاء مسموح وقد يؤثر على تقييم الحساب الداخلي — **بدون** ذكر مبلغ رسوم.
3. بعد النجاح: `ride.cancelled` مع `cash_fee: false`.

### الأوقات المحفوظة على الخادم

`created_at` · `assigned_at` · `arrived_at` · `cancelled_at` · `cancel_actor_role` · `cancel_score_event` (+ تدقيق `ride.cancelled_by_customer`).

## 14. موقع التقاء خاطئ

### ما يوفره الباك

| القدرة | التفاصيل |
| --- | --- |
| إنشاء مع مصدر | `POST /customer/rides` حقل اختياري `pickup_source`: `PIN` \| `GPS` \| `SEARCH` \| `SAVED_PLACE` |
| تصحيح الالتقاء | `PATCH /customer/rides/:rideId/pickup` جسم: `{ lat, lng, address?, source? }` |
| متى يُسمح | فقط `SEARCHING` \| `DRIVER_ASSIGNED` \| `DRIVER_EN_ROUTE` — **ليس** بعد `ARRIVED` |
| إعادة تقدير | يحدّث المسار/الأجرة التقديرية مثل تعديل الوجهة |
| إشعار السائق | Socket `ride.pickup_updated` |
| التدقيق | كل تعديل يُسجَّل للمراجعة الإدارية |

```json
{
  "ride_id": "…",
  "pickup": { "lat": 33.5, "lng": 36.3, "address": "…", "source": "GPS" },
  "pickup_updated_at": "…",
  "estimated_distance_m": 4200,
  "estimated_duration_sec": 720,
  "estimated_fare": 195
}
```

### واجهة العميل

1. عند اختيار الالتقاء: أرسل `pickup_source` الصحيح (لا تضع `GPS` إذا سحب الدبوس يدوياً).
2. قبل الوصول: زر «تصحيح نقطة الالتقاء» أو «مشاركة موقعي الحالي» → `source: GPS`.
3. بعد `ARRIVED`: أخفِ التصحيح؛ وجّه للتواصل عبر المحادثة/الاتصال.
4. اعرض على الخريطة: دبوس الالتقاء الحالي + تمييز إن عُدّل (`pickup_updated_at != null`).

### واجهة السائق

1. قبل الوصول: خريطة بنقطة الالتقاء من الرحلة النشطة + المسافة بين موقع السائق الحي ونقطة الالتقاء (حساب محلي من GPS السائق و`pickup_lat/lng`).
2. عند `ride.pickup_updated`: حدّث الدبوس والملاحة فوراً + Snackbar «عدّل الراكب نقطة الالتقاء».
3. شارك/افتح في تطبيق الخرائط الخارجي من إحداثيات الالتقاء الحالية (ليست GPS السائق).
4. ميّز في التفاصيل إن وُجد `pickup_source` (مثل «من GPS الراكب» مقابل «دبوس على الخريطة») — للعرض فقط.

### ما لا تفعله

- لا تسمح بتعديل الالتقاء من تطبيق السائق (العميل فقط).
- لا تفترض تعويضاً عند بُعد الدبوس الأصلي.

## 16. اتهام بالتأخر / عدم الوصول — سجل زمني

### للوحة الإدارة (مرجع؛ الداشبورد جاهز)

`GET /api/v1/go/erp/rides/:rideId/timeline`

يعيد أحداثاً مشتقة + `caveats` مثل `GPS_NOT_CONCLUSIVE` و`ARRIVED_IS_DRIVER_MARKED`.

أنواع الأحداث: `CREATED` · `OFFERED` · `ASSIGNED` · `EN_ROUTE` (مستنتج) · `ARRIVED` · `STARTED` · `COMPLETED` · `CANCELLED` · `NO_SHOW` · `PICKUP_UPDATED`.

### لتطبيق السائق / العميل

لا حاجة لبناء شاشة timeline كاملة في الموبايل في هذه المرحلة. يكفي:

1. السائق: عند الضغط «وصلت» استخدم `POST .../arrive` فقط — لا تعتمد على «أنا داخل نصف القطر» كدليل نزاع.
2. احتفظ محلياً أثناء الرحلة بعرض أوقات الحالة القادمة من الخادم (`assigned_at`, `arrived_at`) إن وُجدت في `GET /driver/rides/active`.
3. عند الشكوى لاحقاً: الإدارة تفتح السجل من الداشبورد.

### دقة GPS والشبكة

- أحداث Socket قد تتأخر — بعد إعادة الاتصال: `GET /driver/rides/active` (و`/customer/...` للعميل).
- لا تعرض للراكب «السائق وصل» إلا بعد حدث/حالة `ARRIVED` من الخادم.

---

## سادساً — الإدارة تحل نيابةً عن السائق (خلاف مالي)

| حاجة الإدارة | أين في النظام |
| --- | --- |
| سجل الرحلة الزمني | `/erp/rides/:id` → بطاقة «السجل الزمني» أو `GET .../timeline` |
| محفظة السائق وتفاصيل الحركات | `/erp/wallets/:driverId` |
| تعويض على رحلة (يقلل مستحق العميل؛ المالية تحدد التحمل) | `/erp/finance/compensation` |
| عكس حركة محفظة | ERP عكس المعاملات (صلاحية مالية) |

### تطبيق السائق

- شاشة المحفظة تبقى ملخصاً (`GET /driver/wallet` — **بدون** سجل كامل حسب تصميم §20.9).
- عند خلاف: «تواصل مع الدعم» + رقم الرحلة / المرجع. لا تبنِ شاشة تسوية مالية محلية تخمّن المستحق.
