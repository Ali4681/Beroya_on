# تذكرة Flutter — Beroya Radar للسائق + المرونة عند انقطاع الاتصال

موجّهة لمطوّر تطبيق السائق (والعميل في القسم 4–7).
الـBackend جاهز ومختبر في `Beroya_on`. **لم يُنفَّذ أي شيء في تطبيق Flutter بعد.** ادمج داخل مشروعكم الحالي وبنفس الـarchitecture.

مرجع الأرقام والتعريفات: `RADAR_COMMAND_CENTER.md`.

---

## القواعد غير القابلة للنقاش

1. الرادار **معلومة فقط**. لا يغيّر التوزيع ولا السعر ولا العمولة، ولا يعد السائق بأي رحلة.
2. لا تعرض أرقاماً غير موجودة في الاستجابة. إذا `forecast_requests == null` اعرض "لا يوجد توقع"، وليس صفراً.
3. لا تسمِّ الطلبات الأخيرة "توقعاً".
4. لا طابور offline لعمليات حرجة أو مالية (قبول عرض، بدء/إنهاء رحلة، إلغاء، شحن محفظة). أثناء الانقطاع: الزر معطّل مع رسالة.
5. لا تخزّن توكنات أو بيانات مالية في `SharedPreferences`. التوكنات في `flutter_secure_storage` (أو المكافئ الموجود لديكم).

## 1. شاشة Radar للسائق

### API

`GET /api/v1/go/driver/radar?lat=&lng=&radius_m=`

- `lat`/`lng` اختياريان؛ إذا حُذفا يُستخدم آخر موقع مُرسل.
- `radius_m`: 500–10000، الافتراضي 5000.
- حد 30 طلب/دقيقة. عند `429` + `code: RATE_LIMITED` لا تُعِد المحاولة فوراً؛ انتظر للدقيقة التالية.
- `VALIDATION_ERROR` إذا لا يوجد موقع: اطلب تفعيل الموقع.

```json
{
  "generated_at": "2026-10-15T10:30:00.000Z",
  "location": { "lat": 33.51, "lng": 36.27, "source": "request" },
  "radius_m": 5000,
  "resolution": 8,
  "observed_window": { "from": "...", "to": "..." },
  "forecast": { "status": "ok", "reason": null, "horizon": { "from": "...", "to": "..." }, "method": "..." },
  "cells": [
    {
      "cell": "88...",
      "center": { "lat": 33.5, "lng": 36.29 },
      "boundary": [[33.5, 36.28], [33.51, 36.29]],
      "level": "high",
      "heat": 5,
      "forecast_heat": 4,
      "recent_requests": 7,
      "waiting_requests": 2,
      "forecast_requests": 4.5,
      "distance_m": 1800
    }
  ],
  "suggestions": [
    { "cell": "88...", "center": { "lat": 33.5, "lng": 36.29 }, "distance_m": 1800, "score": 8.5, "reasons": ["WAITING_REQUESTS", "FORECAST_DEMAND"] }
  ],
  "notice": "NO_GUARANTEE"
}
```

| الحقل | المعنى للسائق |
| --- | --- |
| `recent_requests` | طلبات آخر 60 دقيقة (تاريخ، ليس توقعاً) |
| `waiting_requests` | طلبات تبحث عن سائق **الآن** |
| `forecast_requests` | متوقع للساعة القادمة، أو `null` |
| `heat` | درجة اللون 0–5 للطلب (الأكبر بين طلبات آخر ساعة والطلبات المنتظرة الآن؛ 5 = الأكثر). نسبية داخل المنطقة المعروضة |
| `forecast_heat` | درجة اللون 0–5 للتوقع، أو `null` إذا لا يوجد توقع |
| `level` | `high` / `medium` / `low` / `none` — للتوافق فقط؛ استخدم `heat` للتلوين |
| `reasons` | `WAITING_REQUESTS` · `FORECAST_DEMAND` · `RECENT_DEMAND` |
| `forecast.status` | `ok` أو `insufficient_data` (`reason`: `NOT_ENOUGH_HISTORY` / `TOO_FEW_REQUESTS`) |

### الواجهة

- خريطة حرارية سداسية (نفس مكتبة الخرائط الموجودة): مضلع لكل `boundary`، لونه حسب `heat`، حد أبيض رفيع، شفافية ≈ 0.72. `heat == 0` بدون تعبئة.

```dart
const heatColors = [
  Color(0xFFC6F6FA), // 1 أقل
  Color(0xFF7AE6F0), // 2
  Color(0xFF22C7D6), // 3
  Color(0xFF1F8D99), // 4
  Color(0xFF0C4D57), // 5 أكثر
];
Color? heatColor(int heat) => heat <= 0 ? null : heatColors[heat.clamp(1, 5) - 1].withOpacity(0.72);
```

- مفتاح ألوان صغير: "أقل ▢▢▢▢▢ أكثر".
- مفتاح "توقع" يبدّل التلوين إلى `forecast_heat` (معطّل إذا `forecast.status == insufficient_data`).
- بطاقة "أقرب مناطق مطلوبة" من `suggestions` (حتى 3) مع المسافة والسبب.
- زر "اذهب" يفتح الملاحة الخارجية فقط. لا يغيّر حالة السائق.
- نص ثابت ظاهر: "هذه معلومات عن الطلب، وليست ضماناً لرحلة."
- `forecast.status == insufficient_data`: شارة "لا يوجد توقع بعد" وإخفاء طبقة التوقع.
- `cells` فارغة: "لا طلبات قريبة الآن".
- اعرض عمر البيانات من `generated_at` ("محدّث قبل 40 ث").

### التحديث

- عند فتح الشاشة، ثم كل 60 ث **فقط والشاشة ظاهرة** والتطبيق في المقدمة.
- سحب للتحديث مع debounce (≥ 5 ث).
- لا تستدعِ الرادار في الخلفية.
- أثناء رحلة نشطة: أخفِ الشاشة أو اجعلها للقراءة فقط.

## 2. حالة الاتصال (عميل + سائق)

ثلاث حالات ظاهرة في الرأس:

| الحالة | متى | العرض |
| --- | --- | --- |
| `online` | Socket متصل + الشبكة متاحة | نقطة خضراء |
| `reconnecting` | Socket يحاول | "إعادة الاتصال…" |
| `offline` | لا شبكة (`connectivity_plus` إن وُجد) أو فشل متكرر | شريط "غير متصل — البيانات قد تكون قديمة" |

أي بيانات معروضة من الكاش تحمل "آخر تحديث: ...".

### 2.1 Offline Resilience أثناء الرحلة (السائق)

المشكلة: ينقطع الإنترنت فلا يستطيع السائق تحديث حالة الرحلة أو إرسال موقعه بصورة طبيعية.

| المطلوب | التنفيذ |
| --- | --- |
| اكتشاف انقطاع الاتصال | `connectivity_plus` + فشل Socket/HTTP المتكرر → حالة `offline` / `reconnecting` |
| إظهار حالة الاتصال بوضوح | شريط ثابت فوق شاشة الرحلة النشطة (لا يُخفى خلف الملاحة) |
| الاحتفاظ بآخر حالة معروفة للرحلة | كاش محلي لـ `GET /driver/rides/active`؛ اعرضه ولا تفرّغ الشاشة |
| وقت آخر تحديث للموقع | من آخر نقطة GPS ناجحة محلياً (أو آخر `recorded_at` أُرسل) — نص نسبي يُحدَّث كل ثانية |
| إعادة الاتصال تلقائياً | Socket `enableReconnection` + backoff (القسم 3) |
| استعادة حالة الرحلة عند العودة | بعد `connect`: `GET /driver/rides/active` + `GET /driver/availability` ثم امسح/حدّث الكاش |
| منع تكرار الطلبات | `Idempotency-Key` + `GET /operations/{key}` (القسم 4) — لا طابور offline لقبول/بدء/إنهاء/إلغاء |

نص الشريط المقترح (عربي):

```
⚠️ الاتصال بالإنترنت منقطع.
آخر تحديث لموقعك: منذ 30 ثانية.
نحاول إعادة الاتصال...
```

سلوك الأزرار أثناء `offline` / `reconnecting`:

- **معطّلة مع رسالة:** وصل / بدء / إنهاء / إلغاء / قبول عرض (لا طابور؛ القسم القواعد #4).
- **مستمرة محلياً:** تسجيل نقاط GPS في طابور الموقع (القسم 5) حتى تعود الشبكة.
- عند عودة `online`: ارفع الدفعة، ثم استعد الرحلة من REST، ثم فعّل الأزرار حسب الحالة المستعادة.

لا تعتمد على أن السائق ضغط «إعادة المحاولة» — إعادة الاتصال تلقائية؛ الزر اليدوي اختياري فقط إذا بقي `offline` > 30 ث.

## 3. Socket.IO — إعادة الاتصال

Namespaces: `/go/driver` و `/go/customer`. التوكن في `auth: { token }`.

```dart
final socket = io.io('$origin/go/driver', io.OptionBuilder()
    .setTransports(['websocket'])
    .disableAutoConnect()
    .enableReconnection()
    .setReconnectionDelay(1000)
    .setReconnectionDelayMax(20000)
    .setRandomizationFactor(0.5)
    .setAuthFn((cb) async => cb({'token': await tokens.accessToken()}))
    .build());
```

إذا مكتبتكم لا تدعم `authFn`، حدّث `socket.auth` قبل كل `connect()`.

- `connect_error` برسالة `UNAUTHORIZED`: جدّد التوكن عبر `POST /auth/refresh` (مع `Idempotency-Key`) ثم `connect()`. حد أقصى محاولتان ثم أرسل المستخدم لتسجيل الدخول.
- `disconnect` بسبب `io server disconnect`: أعد الاتصال يدوياً.
- **بعد كل إعادة اتصال:** اجلب الحالة من REST لأن الأحداث الفائتة لا تُعاد:
  - السائق: `GET /driver/rides/active` + `GET /driver/availability` + `GET /driver/offers`
  - العميل: الرحلة الحالية
- لا تعتمد على ترتيب الأحداث. اعتبر REST هو الحقيقة.

أحداث السائق المهمة: `ride.offer` · `ride_offer.created` · `ride_offer.expired` · `ride_offer.taken` · `ride.assigned` · `ride.customer_cancelled` · `ride.staff_cancelled` · `ride.route_updated` · `ride.stop_updated` · `ride.pickup_updated` · `ride.interrupted` · `ride.breakdown_reported` · `driver.forced_offline` · `wallet.updated`.  
تعطّل السيارة: انظر `FLUTTER_BREAKDOWN.md` (`POST /driver/rides/:id/breakdown`).

## 4. Idempotency — العمليات الحرجة

هذه المسارات تتطلب `Idempotency-Key` (8–128 حرفاً):

| السائق | العميل |
| --- | --- |
| `POST /driver/offers/:offerId/accept` | `POST /customer/rides` |
| `POST /driver/rides/:rideId/start` | `POST /customer/rides/:rideId/cancel` |
| `POST /driver/rides/:rideId/end` | `POST /customer/rides/:rideId/complaints` |
| `POST /driver/rides/:rideId/cancel` | `POST /customer/support/messages` |
| `POST /driver/rides/:rideId/no-show` | |
| `POST /auth/refresh` · `POST /auth/logout` | `DELETE /customer/account` |

القاعدة: **مفتاح واحد لكل عملية منطقية**، وليس لكل محاولة HTTP.

```
المستخدم ضغط "إنهاء الرحلة"
  → key = uuid v4، احفظه في الذاكرة (أو تخزين آمن) مع اسم العملية
  → POST مع Idempotency-Key: key
  → نجاح: احذف المفتاح
  → timeout / انقطاع (النتيجة مجهولة):
       GET /operations/{key}
         COMPLETED   → استخدم response (العملية تمّت)، احذف المفتاح
         IN_PROGRESS → انتظر 1–2 ث واسأل مجدداً، لا ترسل مفتاحاً جديداً
         NOT_FOUND   → لم تُطبّق؛ أعد الإرسال **بنفس المفتاح**
  → 4xx واضح (غير 409 IN_PROGRESS): احذف المفتاح واعرض الخطأ
```

| الكود | HTTP | التصرف |
| --- | --- | --- |
| `IDEMPOTENCY_KEY_REQUIRED` | 400 | خطأ برمجي عندكم |
| `IDEMPOTENCY_KEY_REUSED` | 422 | نفس المفتاح بجسم مختلف — خطأ برمجي |
| `IDEMPOTENCY_IN_PROGRESS` | 409 | انتظر ثم `GET /operations/{key}` |

الاستجابة المعادة تحمل header `Idempotent-Replayed: true`.

- لا إعادة تلقائية في الخلفية بعد إغلاق الشاشة لعمليات مالية.
- إعادة المحاولة فقط والمستخدم ما زال على الشاشة، أو بزر "إعادة المحاولة".
- المفاتيح تنتهي بعد 24 ساعة.

### 4.1 مزامنة موثوقة لقبول العرض (السائق)

المشكلة: يظهر طلب ثم يختفي، أو يضغط السائق «قبول» ولا يعرف هل قُبل فعلاً.

| المطلوب | التنفيذ |
| --- | --- |
| حالة واضحة أثناء القبول | فور الضغط: عطّل الزر، أظهر «جارٍ قبول الرحلة…»، لا تغلق البطاقة |
| التحقق من النتيجة من الخادم | نجاح `POST /driver/offers/:offerId/accept` → انتقل لشاشة الرحلة من الاستجابة؛ لا تعتمد على Socket وحده |
| منع قبول نفس الرحلة من أكثر من سائق | الخادم يقفل ذرياً (`ride-accept:{rideId}`)؛ الخاسر يحصل `RIDE_ALREADY_TAKEN` (409) |
| تحديث العرض إذا قبله آخر | استمع لـ `ride_offer.taken` و `ride_offer.expired` → أغلق البطاقة مع رسالة مناسبة |
| انقطاع أثناء القبول | نفس مفتاح Idempotency → `GET /operations/{key}`؛ أو عند العودة: `GET /driver/rides/active` + `GET /driver/offers` |
| ضغطات متعددة | مفتاح واحد لكل ضغط «قبول» منطقي؛ تجاهل الضغطات اللاحقة بينما الحالة `accepting` |

مصادر الحقيقة (بالترتيب عند الشك):

1. `GET /operations/{key}` إن وُجد مفتاح قبول معلّق.
2. `GET /driver/rides/active` — إن وُجدت رحلة مُسندة فالقبول نجح.
3. `GET /driver/offers` — إن اختفى العرض وليس لديك رحلة نشطة فالعرض انتهت صلاحيته أو أخذه غيرك.

أحداث Socket أثناء وجود بطاقة عرض:

| الحدث | تصرف الواجهة |
| --- | --- |
| `ride_offer.created` / `ride.offer` | اعرض/حدّث البطاقة |
| `ride_offer.expired` | أغلق البطاقة: «انتهى وقت العرض» |
| `ride_offer.taken` | أغلق البطاقة: «قبلها سائق آخر» |
| `ride.assigned` | أكّد النجاح وانتقل لشاشة الرحلة |

رسائل مقترحة:

```
جارٍ قبول الرحلة…
قبلها سائق آخر
انتهى وقت العرض
تعذّر التأكد — نتحقق من الخادم…
```

لا تُظهر «فشل القبول» عند timeout قبل استعلام `/operations` أو REST — النتيجة قد تكون نجحت على الخادم.

## 5. الموقع أثناء الانقطاع (السائق)

- `POST /driver/location` لكل نقطة حيّة، **دائماً مع `recorded_at`** (وقت GPS، ISO UTC).
- أثناء الانقطاع: خزّن النقاط محلياً (ليست بيانات حساسة مالياً، لكن امسحها عند تسجيل الخروج).
- عند العودة: `POST /driver/location/batch` بـ `{ "points": [...] }`، دفعات ≤ 500 نقطة، الأقدم أولاً.
- السيرفر يرفض النقاط الأقدم من 24 ساعة أو الأحدث من 5 دقائق في المستقبل، ويحذف المكرر.

الاستجابة:

| الحقل | المعنى |
| --- | --- |
| `applied: false` | نقطة أقدم من آخر موقع معروف؛ حُفظت في المسار لكن لم تغيّر الموقع الحي. **ليس خطأ.** |
| `clock_adjusted: true` | ساعة الجهاز متقدمة؛ استخدم وقت السيرفر للعرض |
| `live_applied` (batch) | هل أحدث نقطة في الدفعة غيّرت الموقع الحي |
| `accepted` / `rejected` / `duplicates_removed` | للتشخيص |

لا تُعِد إرسال نفس الدفعة بعد نجاحها. إذا فشل الطلب أعد نفس النقاط (السيرفر يحذف المكرر).

## 6. المؤشرات القديمة (Stale)

- أي رقم/خريطة من كاش أقدم من 2 دقيقة: نص رمادي "قديم" + وقت آخر تحديث.
- موقع السائق الخاص به: إذا GPS لم يُحدَّث > 60 ث اعرض "GPS ضعيف".
- عند `offline`: عطّل أزرار العمليات الحرجة (القسم 4) بدلاً من وضعها في طابور.

---

## 7. الكاش وتسجيل الخروج

- عند تسجيل الخروج أو تبديل الحساب: امسح كاش الطلبات، الرادار، نقاط الموقع المعلّقة، مفاتيح idempotency، وأغلق الـsocket.
- لا تعرض بيانات حساب سابق ولو لحظة.
- التوكنات فقط في التخزين الآمن. رصيد المحفظة يُجلب من السيرفر ولا يُخزَّن دائماً.

## 8. معايير القبول

- [ ] Radar يعرض المناطق والاقتراحات من الـAPI فقط، مع نص "ليس ضماناً".
- [ ] `forecast_requests == null` يظهر "لا يوجد توقع"، لا صفر.
- [ ] 429 لا يسبب حلقة طلبات.
- [ ] أثناء رحلة نشطة وقطع الشبكة: يظهر شريط Offline مع آخر تحديث للموقع و«نحاول إعادة الاتصال»، وتبقى آخر حالة رحلة ظاهرة، وأزرار وصل/بدء/إنهاء معطّلة.
- [ ] قطع الشبكة 30 ث ثم إعادتها: الحالة تمر reconnecting ثم online، والرحلة النشطة تُجلب من REST.
- [ ] توكن منتهٍ أثناء الانقطاع: يُجدَّد ويعود الاتصال بدون تسجيل خروج.
- [ ] إنهاء رحلة مع قطع الشبكة بعد الإرسال: `GET /operations/{key}` يحدد النتيجة؛ لا تُنهى الرحلة مرتين.
- [ ] قبول عرض بضغطتين سريعتين: طلب واحد فعلي (نفس المفتاح) + واجهة «جارٍ قبول الرحلة…».
- [ ] قبول مع قطع الشبكة بعد الإرسال: `/operations/{key}` أو REST يحدد إن نجحت؛ لا رسالة فشل كاذبة.
- [ ] `ride_offer.taken` / `expired` يغلقان البطاقة برسالة واضحة دون بقاء عرض شبح.
- [ ] سائقان يقبلان معاً: واحد ينجح والآخر يرى `RIDE_ALREADY_TAKEN` أو `ride_offer.taken`.
- [ ] 10 دقائق offline أثناء رحلة: الدفعة تُرسل عند العودة والمسار مكتمل.
- [ ] ساعة الجهاز متقدمة 10 دقائق: لا تتعطل الواجهة، `clock_adjusted` يُعالج.
- [ ] تسجيل خروج ثم دخول بحساب آخر: لا بيانات من الحساب الأول.
- [ ] لا توكنات في `SharedPreferences`.

## 9. خارج النطاق

- لوحة مركز القيادة (داشبورد الويب فقط).
- أي تغيير في التسعير/التوزيع.
- إشعارات push للرادار (غير مطلوبة الآن).
